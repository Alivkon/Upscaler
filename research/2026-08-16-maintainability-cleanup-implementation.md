## Цель

Сделать репозиторий пригодным для того, чтобы следующий агент писал в нём
код, не ухудшая его. Агент выбирает стиль, глядя на соседний код, и верит
тому, что написано в `AGENTS.md`. Значит, до появления нового кода нужно,
чтобы соседний код был читаемым, а инструкция — правдивой.

## Принятые решения

**Форматирование отдельным коммитом.** `bb56ed6` — чистый вывод
`yarn format`, ни одной правки по смыслу. Его SHA лежит в
`.git-blame-ignore-revs`, поэтому `git blame` продолжает показывать
настоящего автора строк. Включается один раз на машину:

```bash
git config blame.ignoreRevsFile .git-blame-ignore-revs
```

**Команда проверки называется `verify`, а не `check`.** `yarn check` —
встроенная команда yarn 1: она перекрывает одноимённый скрипт и завершается
успешно, ничего не проверив. Это та же ловушка, из-за которой в `AGENTS.md`
оказался несуществующий `yarn build`.

**Ошибки разделены на предназначенные посетителю и все остальные.**
Введён класс `HttpError(status, message)`. Наружу уходит только его текст;
любая другая ошибка превращается в «Внутренняя ошибка сервера» и пишется
в лог. Маршруты больше не отвечают на ошибки сами — все зовут `next(error)`.

**Изображения сняты с учёта, каталоги оставлены** через `.gitkeep`.
Фотографии живут на сервере.

**Имя пакета — нейтральное `upscaler`.** `topaz-x2-upscaler` называл сервис,
которого в коде давно нет. Название продукта выбирается сейчас отдельно,
и здесь его лучше не опережать.

## Что изменилось в поведении

Два изменения, оба намеренные.

1. **Ссылка на результат.** Было `/outputs/<файл>`, стало
   `/images/generated/<файл>` — тот же каталог под одним именем. Фронтенд
   берёт ссылку из ответа API, правок в `public/` не потребовалось. Внешние
   ссылки на `/outputs/…`, если они где-то сохранены, перестанут работать;
   домена и индексации пока нет, поэтому момент для смены удачный.
2. **Текст ошибки для посетителя.** Раньше `/api/upscale` показывал
   `error.message` как есть — включая «Добавьте действительный
   REPLICATE_API_TOKEN в файл .env». Теперь такие сообщения идут в лог.

Отдельно: после свежего `git clone` коллекция будет пуста, пока фотографии
не положены в `images/storage` на сервере. Страница отрисует пустую сетку,
ошибки не будет.

## Ограничения

Реальные вызовы Replicate не выполнялись — они платные. Успешный путь
`/api/upscale` (создание задачи, ожидание, скачивание, сохранение) проверен
только до места, где требуется токен. Имя файла результата с `slug` модели
и запись в `images/generated` на живом вызове не проверялись.

`.git` по-прежнему весит 68 МБ: снятие с учёта не удаляет объекты из
истории. Уменьшить размер может только перезапись истории
(`git filter-repo` или BFG), а она ломает все существующие клоны —
это решение владельца репозитория.

Не сделано намеренно: ограничения на платный `/api/upscale`; запрос длиной
до 10 минут против таймаутов прокси в 30–100 секунд; общий шаблон
для HTML-страниц.

## Витрина: файл-индекс (вопрос 4, одобрен)

### Что было не так

Порядок карточек задавался временем изменения файла. Время изменения
не переживает клонирование — git ставит всем файлам время выгрузки,
и у всех десяти стартовых карточек оно совпадало с точностью до
миллисекунд. Порядок, который видел посетитель, был порядком записи файлов
на диск, а не чьим-то решением, и после нового клона мог оказаться другим.

Побочно: каждая картинка лежала на диске в двух-трёх копиях. Продвижение
из пула копировало файл в `images/gallery` с префиксом `llm-<время>-`,
публикация результата — в `images/shared`. Время добавления кодировалось
в имени файла и потом разбиралось регулярным выражением.

### Что сделано

`images/gallery.json` — список записей `{ file, source, added }`. Порядок
в файле и есть порядок на странице; новая работа добавляется в начало.
Чтобы закрепить работу первой, достаточно передвинуть строку. Файлы больше
не копируются: запись ссылается на уже существующий файл.

Пул раздаётся отдельным маршрутом `/images/storage` до общего `/images`.
Это чинит `INTERNAL_IMAGE_STORAGE_DIR`: раньше пул вне проекта работал
только потому, что файлы из него копировались внутрь `images/`.

`gallery` и `shared` остались доступны только на чтение — у работающих
установок там лежат уже опубликованные работы. При первом запуске без
индекса он собирается из содержимого этих каталогов по времени файла,
то есть ровно в том порядке, который посетитель видит сейчас. Записи вида
`gallery/llm-<время>-<имя>` считаются показанным исходником, иначе после
переноса пул пошёл бы по второму кругу.

Индекс правится руками, поэтому `resolveEntryPath` проверяет каждую запись,
а изменения идут по очереди — два одновременных запроса иначе затрут
работу друг друга.

### Разделение файлов

После этого `server.js` дошёл до 391 строки — тот самый повод остановиться
и посмотреть, про который написано в `AGENTS.md`. Работа с изображениями
оказалась связным куском с понятным именем, поэтому выделен `gallery.js`
(168 строк), а `server.js` вернулся к 253 и остался про HTTP и Replicate.
Это разделение по шву, а не сжатие строк ради счётчика; список швов
в `AGENTS.md` обновлён — следующий `replicate.js`.

### Проверки

На живом сервере, до и после выделения `gallery.js` — одинаково:

- перенос со старой схемы: 10 карточек, первой `llm-1786864308230-…`,
  в индексе 11 записей — тот же порядок, что был виден до изменения;
- `POST /api/gallery/refresh`: записей 11 → 12, файлов в `images/gallery`
  11 → 11 (копии нет); продвинутая работа отдаётся по своему URL:
  HTTP 200, 4186116 байт;
- «пример гравировки2.jpg» уже показан как `gallery/llm-…` и из пула
  повторно не всплыл: записей с этим именем 1;
- публикация результата: первая карточка `generated/test-result-x2-1.png`
  `[shared]`, файлов в `images/shared` — 0; повторная публикация того же
  файла дубля не создала;
- пять одновременных `refresh`: записей 18 → 23, дубликатов 0;
- индекс с записями `../../../etc/passwd`, `gallery/../../server.js`,
  `secrets/.env` и ссылкой на удалённый файл — все четыре пропущены,
  витрина вернула 10 корректных карточек;
- `INTERNAL_IMAGE_STORAGE_DIR` во внешнем каталоге: работа из пула
  отдаётся по `/images/storage/external-photo.png`, HTTP 200.

### Ограничение

Индекс `images/gallery.json` — состояние работающего сервера, он
в `.gitignore`. После свежего клона его нет; он соберётся при первом
обращении к витрине из того, что лежит в каталогах на сервере.
