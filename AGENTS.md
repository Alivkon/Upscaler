# Как работать в этом проекте

Файл для того, кто пришёл сюда впервые — человека или агента. Правила
короткие, но у каждого есть причина; причина важнее самого правила, потому
что она подскажет, что делать в случае, который здесь не описан.

## Запуск и проверка

```bash
yarn install     # зависимости
yarn start       # сервер на http://127.0.0.1:3000
yarn dev         # то же с перезапуском при изменении файлов
yarn verify      # проверка перед коммитом: синтаксис + форматирование
yarn format      # расставить форматирование по правилам проекта
```

Шага сборки нет. `yarn build` не существует и никогда не существовал —
если встретите его в старой документации или в чужом ответе, это ошибка.
Проверить список команд можно в `scripts` внутри `package.json`.

Команда проверки называется `verify`, а не `check`: `yarn check` — встроенная
команда yarn 1, она перекрывает одноимённый скрипт и завершается успешно,
ничего не проверив.

## Код

**`public/` — это исходник, а не результат сборки.** Браузер получает
`app.js`, `index.html` и `styles.css` ровно такими, какими они лежат в
репозитории. Значит, сжимать их незачем: выигрыша в скорости нет, а diff
и `git blame` перестают работать. Форматирование задаётся `.prettierrc.json`
и проверяется `yarn verify`, так что решать этот вопрос заново не нужно —
достаточно запустить `yarn format`.

**Правьте точечно.** Менять нужно те строки, которые относятся к задаче.
Переписывание файла целиком выглядит как решение, но у него две цены: в diff
не видно, что именно изменилось, и вместе с текстом переписывается стиль —
новый автор выбирает его, глядя на соседние файлы, и незаметно уносит проект
в сторону. Так `public/app.js` за один коммит сжался с 73 строк до 7.

**Не оставляйте мёртвый код.** Ветка `if (model.version)`, для которой ни
одна запись не задаёт `version`, читается как «бывают модели с версией» —
это ложная документация, и следующий читатель потратит время, разбираясь
в несуществующем случае. Если код не выполняется — удалите его; история
в git сохранится.

**Одно имя на одну сущность.** Было три названия одного каталога:
`outputs/` на диске, `OUTPUTS_DIR` и `GENERATED_DIR` в коде, `/outputs`
в URL. Каждый синоним — повод для вопроса «а это то же самое или другое?».

**Строки, зависящие от модели, живут только в `MODEL`.** Имя, эндпоинт,
`slug` для имени файла — всё в одном месте. Иначе получается то, что было,
пока моделей было несколько: результат Nano Banana сохранялся
с `-real-esrgan-` в имени файла.

**Ошибки.** Маршруты не отвечают на ошибки сами, а передают их дальше:
`next(error)`. Централизованный обработчик в конце `server.js` решает, что
показать. Наружу уходит только текст `HttpError` — он написан для посетителя;
всё остальное превращается в «Внутренняя ошибка сервера» и пишется в лог.
Это не формальность: раньше посетитель мог увидеть «Добавьте действительный
REPLICATE_API_TOKEN в файл .env».

## Размер файлов и функций

Ориентир: файл — около 400 строк, функция — около 50. Это **повод
остановиться и посмотреть**, а не запрет. Иногда функция на 70 строк —
честное описание последовательности шагов, и дробить её вредно.

Важно, как именно уменьшать. Разделять нужно по швам — по границе
ответственности, где у куска кода появляется собственное имя и его можно
объяснить одной фразой. Сжатие строк, удаление переносов и однобуквенные
имена уменьшают счётчик и ничего не улучшают; это не рефакторинг.

По этому шву уже разделено: `gallery.js` — где лежат изображения и что
показано на витрине. `server.js` знает про HTTP и Replicate и зовёт оттуда
`galleryItems`, `promoteNextStorageImage`, `publishGeneratedImage`.

Следующие швы, когда файлы снова вырастут:

- `server.js` → `replicate.js` (`apiHeaders`, `parseResponse`,
  `createPrediction`, `waitForResult`, `saveResult`);
- `public/app.js` → коллекция, студия, лайтбокс.

Не создавайте `utils.js`, `helpers.js` и `common.js`: в такой файл попадает
всё подряд, потому что его название ничего не запрещает.

## Изображения и файлы

Каталоги `images/*` есть в репозитории, их содержимое — нет. Сервер создаёт
эти файлы во время работы, а коллекция живёт на сервере. Не добавляйте
изображения в коммит через `git add -f`.

Имена файлов — только латиница, цифры и дефис, без пробелов и заглавных.
Такие имена уже появлялись: ` case1-after.jpg` в `images/gallery` и удалённый
`public/ CODEX.md` — оба с пробелом в начале. Пробел в имени не виден глазом,
ломает команды в терминале и требует кавычек везде, где имя встречается.

Двоичные файлы — отдельным коммитом от кода. В коммите `23f5ba7` правка
`public/app.js` оказалась среди 99 картинок, и её никто не увидел в ревью.

Никогда не запускайте `git add -A`: в рабочем каталоге бывают файлы чужой
незавершённой работы. Добавляйте пути по одному.

## Секреты и деньги

`REPLICATE_API_TOKEN` хранится только в `.env`; `.env` в `.gitignore`,
образец без секретов — в `.env.example`. Не печатайте заголовки запросов
к Replicate: токен передаётся именно в них.

**Каждый вызов Replicate стоит денег.** Не запускайте реальную обработку
изображения, чтобы «просто проверить». Логику вокруг вызова можно проверить
на ошибочных ответах и на маршрутах, которые до Replicate не доходят.
Если проверка требует настоящего вызова — спросите разрешение и напишите,
сколько вызовов планируется.

## Что считается сделанной работой

Задача закрыта, когда:

1. `yarn verify` завершается с кодом 0;
2. проверено то, что менялось, — и в ответ вставлен **настоящий вывод
   команды или измеренный результат**, а не описание «должно работать»;
3. если что-то проверить не удалось, это написано прямо, с причиной.

Фраза «изменения протестированы» без вывода команды не является проверкой.

## Журнал работы

После каждого существенного шага создавайте документ в папке `research`
с именем `YYYY-MM-DD-<тема>.md` и `YYYY-MM-DD-<тема>.html` для
HTML-страницы. В нём:

- цель и принятые решения;
- выполненные изменения с указанием файлов;
- результаты проверок и известные ограничения;
- ссылки на источники, если проводилось исследование.

Записывайте не ход рассуждений, а краткие проверяемые обоснования и
результат. Файлы в `research/` — исторические записи; не переписывайте
старые задним числом.

## Коммиты и совместная работа

Репозиторий общий, и над ним работают параллельно. Перед началом заметной
задачи посмотрите открытые issue и pull request, чтобы не делать одно и то же
дважды. Ветка сама по себе никого не уведомляет — уведомляет pull request.

Коммит должен объяснять, **почему**, а не пересказывать diff. Коммиты,
меняющие только форматирование, делайте отдельно и добавляйте их SHA
в `.git-blame-ignore-revs`, чтобы `git blame` продолжал показывать
настоящего автора строк. Включается это один раз на машину:

```bash
git config blame.ignoreRevsFile .git-blame-ignore-revs
```
